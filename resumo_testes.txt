1.1 — TESTES DE CORRETUDE BÁSICA

  TESTE: Montgomery Ladder — Resultado Consistente
  ────────────────────────────────────────────────

  Objetivo:
    Validar que a multiplicação escalar da escada de Montgomery produz
    resultados idênticos em execuções sucessivas com o mesmo escalar e base.

  Metodologia:
    1. Gera um escalar aleatório k ∈ [2, n-1]
    2. Executa k·Gu (multiplicação de Montgomery) → resultado1
    3. Executa k·Gu novamente com mesmo k → resultado2
    4. Verifica se resultado1 == resultado2 (módulo p)

  Interpretação:
    ✓ PASSAR: Implementação básica está funcional
    ✗ FALHAR: Indicativo de bug em `dadd()`, `scalar_mul()` ou gerenciamento GMP

  Relevância Acadêmica:
    Garante que a base matemática do protocolo X25519 está implementada,
    permitindo avançar para validações mais sofisticadas.

1.2 — TESTES NEGATIVOS (DETECÇÃO DE ADULTERAÇÃO)

  Objetivo:
    Validar que o protocolo AEAD (ChaCha20-Poly1305) REJEITA mensagens
    adulteradas, demonstrando autenticação efetiva.

  Testes Implementados:

  (A) Corrupção de 1 bit no Ciphertext
      ──────────────────────────────────
      Metodologia:
        1. Cifra um payload válido com ChaCha20-Poly1305 → CT, tag
        2. Inverte 1 bit de CT (posição aleatória)
        3. Tenta decifrar CT corrompido com tag válida
        4. Verifica se Decrypt+Verify REJEITA

      Resultado Esperado:
        ✓ Verificação de tag falha (diff_bytes ≠ 0)
        ✗ Decrypt bem-sucedido: BUG em `cc20_dec_verify()`

      Interpretação:
        A tag Poly1305 é função do ciphertext completo. Qualquer alteração
        em um único bit do CT deve alterar a tag esperada, causando rejeição.

  (B) Corrupção de 1 byte na Tag Poly1305
      ────────────────────────────────────
      Metodologia:
        1. Cifra payload válido → CT, tag válida
        2. Inverte 1 byte da tag (posição aleatória)
        3. Tenta decifrar com tag corrompida
        4. Verifica rejeição

      Resultado Esperado:
        ✓ Falha na comparação de tags
        ✗ Aceita tag inválida: BUG crítico

  (C) Mudança de 1 byte no Nonce
      ───────────────────────────
      Metodologia:
        1. Cifra com nonce válido → CT, tag
        2. Decifra com nonce DIFERENTE
        3. Verifica se a operação falha ou produz plaintext incorreto

      Resultado Esperado:
        ✓ Plaintext diferente (ou rejeição)
        ✗ Plaintext original: vulnerabilidade de nonce

  (D) Alteração do AAD (Additional Authenticated Data)
      ────────────────────────────────────────────────
      Metodologia:
        1. Cifra com AAD válido → CT, tag
        2. Tenta decifrar com AAD DIFERENTE
        3. Verifica rejeição

      Resultado Esperado:
        ✓ Tag inválida (AAD alterado muda a tag)
        ✗ Aceita AAD diferente: BUG em `poly1305_buf()`

  Importância Acadêmica:
    Esses testes demonstram que o protocolo oferece autenticação genuína,
    não é apenas confidencialidade. Publicações em segurança IoT exigem
    comprovação de robustez contra ataques simples de adulteração.

1.3 — ANÁLISE DE TIMING PARA CONSTANT-TIME

  Objetivo:
    Investigar se a multiplicação escalar é resistente a ataques de timing
    (i.e., tempo de execução não revela bits do escalar).

  Metodologia:
    1. Gera escalares com diferentes Hamming weights:
       - Hamming weight baixo (ex: 10 bits ativos)
       - Hamming weight médio (ex: 128 bits ativos)
       - Hamming weight alto (ex: 245 bits ativos)

    2. Para cada escalar com peso W:
       - Executa multiplicação escalar 50 vezes
       - Coleta tempos em microssegundos
       - Calcula média e variância

    3. Calcula variância relativa entre grupos:
       V = (σ_alta - σ_baixa) / σ_média

  Interpretação:
    V ≤ 5%  → Implementação parcialmente "constant-time" (adequada para pesquisa)
    V > 15% → Timing leak detectável (inadequada para produção)

  Limitação Importante:
    ⚠️  A implementação GMP utiliza alocação dinâmica e tamanhos variáveis
        de inteiros. Portanto, NÃO oferece constant-time real.
        
        Para constant-time genuíno, seria necessário:
        • Aritmética de campo com limbs fixos (ex: 4×64-bit)
        • Troca condicional sem ramificação
        • Sem acessos a memória dependentes de dados

  Relevância Acadêmica:
    A análise de timing demonstra um ponto fraco conhecido de GMP e motiva
    futuras implementações com aritmética especializada. Mesmo assim, mensura
    o custo dessa escolha.

2.1 — ESCALABILIDADE ARITMÉTICA GMP (MONTGOMERY LADDER)

  Objetivo:
    Medir como o custo da multiplicação escalar escala em função do
    tamanho do primo de campo (e.g., O(n²) vs. O(n³)).

  Metodologia:
    Para cada nível de segurança {80, 112, 128, 192, 224, 256 bits}:
      1. Inicializa Curve25519-like com primo de campo correspondente
         (128-bit usa Curve25519 real; demais usam "substitutos")
      2. Gera escalar aleatório k
      3. Executa multiplicação escalar 3 vezes (warm-up)
      4. Executa 50 vezes, coletando tempo (µs) por iteração
      5. Calcula: média, σ, min, max, P95, P99
      6. Registra pico de memória heap usado pela GMP

  Tabela de Campos Utilizados:
  ┌───────────────┬─────────┬──────────────────────────────────────┐
  │ Segurança     │ Campo   │ Primo de Referência                  │
  ├───────────────┼─────────┼──────────────────────────────────────┤
  │ 80-bit        │ 160-bit │ próximo primo de 2^160               │
  │ 112-bit       │ 224-bit │ NIST P-224                           │
  │ 128-bit (*)   │ 255-bit │ 2^255 - 19 (Curve25519 real)        │
  │ 192-bit       │ 384-bit │ NIST P-384                           │
  │ 224-bit       │ 448-bit │ 2^448 - 2^224 - 1 (Goldilocks)      │
  │ 256-bit       │ 521-bit │ 2^521 - 1 (NIST P-521, Mersenne)   │
  └───────────────┴─────────┴──────────────────────────────────────┘

  Observação Crítica:
    Níveis ≠ 128-bit NÃO representam curvas criptograficamente validadas
    (ex: não há Curve25519 oficialmente de 192 bits). Servem para análise
    de escalabilidade acadêmica.

  Métrica Coletada: Tempo de Execução (µs)

    Operação: k·Gu (um ponto escalar sobre a Escada de Montgomery)
    Iterações: 50 amostras por nível
    Estatísticas: n, média, σ, min, máx, mediana, P95, P99, pico_heap

  Interpretação dos Resultados:

    1. Crescimento de Tempo vs. Tamanho de Campo:
       ────────────────────────────────────────
       Esperado: Crescimento O(n²) a O(n³) conforme tamanho do campo
       
       Típico em GMP:
         • 160-bit:   ~1300 µs
         • 255-bit:   ~3100 µs   (128-bit real, fator ×2.4)
         • 384-bit:   ~7100 µs   (fator ×2.3 desde 255)
         • 521-bit:   ~15000 µs  (fator ×2.1 desde 384)
       
       Razão: Multiplicação de inteiros é O(n²) via Karatsuba;
              redução modular é O(n²) também.
       
       Interpretação:
         ✓ Crescimento consistente: implementação está otimizada internamente
         ✗ Crescimento errático: possível overhead de alocação

    2. Variabilidade (Desvio Padrão):
       ──────────────────────────────
       σ / µ (coeficiente de variação) esperado: 2-5% em sistema ocioso
       
       Se σ / µ > 10%:
         → Sistema sob carga (outros processos)
         → Efeitos de cache variáveis
         → QEMU overhead não-determinístico
       
       Ação: Executar novamente ou desativar outros processos

    3. Pico de Memória Heap:
       ────────────────────
       Registra máximo de bytes alocados simultaneamente pela GMP.
       
       Típico:
         • 80-bit:   ~2 KB
         • 128-bit:  ~3 KB
         • 521-bit:  ~8 KB
       
       Relevância IoT: Dispositivos com RAM < 1 MB precisam verificar
       se pico de heap + stack cabe em orçamento de memória

  Saída CSV:
    label,n,mean_us,std_us,min_us,max_us,median_us,p95_us,p99_us,peak_heap_bytes

2.2 — LATÊNCIA DE PRIMITIVAS INDIVIDUAIS

  Objetivo:
    Isolar o tempo de execução de operações fundamentais.

  Operações Medidas:

  (A) Ed25519 KeyGen
      ───────────────
      Operação: Gerar um par de chaves (privada, pública)
      Entradas: /dev/urandom (32 bytes de sementes)
      Saídas: 64 bytes (privada expandida) + 32 bytes (pública comprimida)
      
      Custo Incluído:
        • Leitura de /dev/urandom
        • SHA-512 da semente
        • Clamping do escalar
        • Multiplicação escalar [s]B em Edwards25519
        • Compressão do ponto resultado
      
      Típico: ~5000-6000 µs (incluindo /dev/urandom)

  (B) Ed25519 Sign
      ────────────
      Operação: Assinar mensagem de 32 bytes com chave privada
      Entrada: Par de chaves (do teste acima) + mensagem
      Saída: Assinatura de 64 bytes (R || S)
      
      Custo Incluído:
        • Geração de nonce r = H(nonce_prefix || M)
        • Multiplicação escalar [r]B
        • Compressão R
        • Cálculo de k = H(R || A || M)
        • Redução modular e aritmética: S = r + k·s mod l
      
      Típico: ~5000-5200 µs
      Nota: Sem geração de aleatoriedade por amostra (setup feito antes)

  (C) Ed25519 Verify
      ───────────────
      Operação: Verificar assinatura válida
      Entrada: Chave pública + mensagem + assinatura válida
      Saída: bool (válida / inválida)
      
      Custo Incluído:
        • Descompressão de R e A
        • Cálculo de k = H(R || A || M)
        • Multiplicação escalar [S]B
        • Multiplicação escalar [k]A
        • Adição de pontos [S]B + [k]A
        • Compressão resultado
        • Comparação constant-time de 32 bytes
      
      Típico: ~10400-10600 µs
      Nota: Verify é ~2× mais lenta que Sign (duas multiplicações escalares)

  (D) HKDF-SHA512
      ────────────
      Operação: Derivar chave de 32 bytes a partir de shared secret
      Entrada: IKM (32 B) + salt (32 B) + info (string)
      Saída: Chave simétrica de 32 B
      
      Custo Incluído:
        • HMAC-SHA512(salt, IKM)  [Extract]
        • HMAC-SHA512(PRK, T || info || ctr)  [Expand, até 64 B]
      
      Típico: ~18-19 µs (muito rápido!)
      Nota: HKDF-SHA512 é operação de derivação, não criptografia pesada

  (E) ChaCha20-Poly1305 Encrypt (por payload)
      ───────────────────────────────────────
      Operação: Cifrar payload de N bytes com autenticação
      Entrada: Chave (32 B) + nonce (12 B) + plaintext (N B) + AAD (0 B)
      Saída: Ciphertext (N B) + tag (16 B)
      
      Tamanhos Testados: 16, 64, 256, 1024, 4096, 16384 bytes
      
      Custo Incluído:
        • Derivação de subchave Poly1305 (bloco ChaCha20 #0)
        • Cifração com ChaCha20 (blocos #1 e seguintes)
        • Construção de buffer de autenticação
        • Computação de tag Poly1305
      
      Típico:
        • 16 B:    ~2-3 µs
        • 64 B:    ~2 µs
        • 256 B:   ~5 µs
        • 1 KB:    ~19 µs
        • 4 KB:    ~73 µs
        • 16 KB:   ~292 µs
      
      Throughput: 16 KB ÷ 0.292 ms ≈ 55 MB/s (em QEMU!)

  (F) ChaCha20-Poly1305 Decrypt+Verify
      ─────────────────────────────────
      Operação: Decifrar e verificar integridade
      Entrada: Chave + nonce + ciphertext (N B) + tag (16 B) + AAD (0 B)
      Saída: Plaintext (N B) ou erro
      
      Custo Incluído:
        • Derivação de subchave Poly1305
        • Recomputação de tag
        • Verificação constant-time de tag
        • Decifragem (apenas se tag válida)
      
      Tipicamente ≈ mesmo custo que Encrypt (operações simétricas)
      Exceção: Verify falha → rejeita sem decifrar (otimização)

  Saída Tabular Esperada:

    Operação                              n   Média (µs)   σ (µs)   P95
    ────────────────────────────────────────────────────────────────────
    Edwards25519 / Ed25519 KeyGen         30   5169.9     205.6   5330.0
    Edwards25519 / Ed25519 Sign           30   5113.7     132.3   5462.0
    Edwards25519 / Ed25519 Verify         30   10480.3    85.9    10598.0
    HKDF-SHA512 (32B → 32B)              500   18.6       11.0    19.0
    CC20-Poly1305 Encrypt (64 B)         500   2.0        0.2     2.0
    CC20-Poly1305 Decrypt (64 B)         500   2.0        0.2     2.0

2.3 — PICO DE MEMÓRIA HEAP (GMP)

  Objetivo:
    Medir quanto de RAM é necessário para cada operação, garantindo que
    o protocolo cabe em dispositivos IoT com restrições.

  Metodologia:
    Injeta hooks customizados em GMP via `mp_set_memory_functions()`:
      • gmp_alloc_hook(): registra alocação
      • gmp_realloc_hook(): registra redimensionamento
      • gmp_free_hook(): registra liberação
    
    Acumula pico máximo durante cada operação.

  Interpretação:
    • Pico ≤ 4 KB:  Excelente (cabe em µcontroladores com 8-32 KB RAM)
    • Pico ≤ 16 KB: Bom (cabe em SBCs e gateways com 64+ MB)
    • Pico > 64 KB: Inadequado para bare-metal IoT

  Relevância IoT:
    Muitos dispositivos IoT (ex: ESP32 com 520 KB RAM) precisam hospedar
    outros módulos (WiFi, TCP/IP). Pico de heap ≤ 8 KB deixa ~500 KB
    disponível para aplicação e stack.

3.1 — LATÊNCIA DE SESSÃO COMPLETA

  Objetivo:
    Medir tempo total de um handshake criptográfico seguido de troca
    de uma mensagem cifrada, representando uma sessão típica IoT.

  Fluxo Medido:

    1. KeyGen Alice (X25519):        ~23 µs
    2. KeyGen Bob (X25519):          ~23 µs
    3. Acordo Diffie-Hellman:        ~3120 µs
    4. HKDF-SHA512 (derivação):      ~18 µs
    5. ChaCha20-Poly1305 Encrypt:    ~2 µs
    6. ChaCha20-Poly1305 Decrypt:    ~2 µs
    ────────────────────────────────────────
    TOTAL (handshake + 1 msg):       ~3188 µs (~3.2 ms)

  Metodologia:
    1. Executa protocolo completo (sem Ed25519) com payload 64 B
    2. Coleta 20 amostras de tempo total
    3. Calcula estatísticas

  Interpretação:

    Latência ≤ 10 ms:   Adequado para IoT intermitente (sensores, alarmes)
    Latência ≤ 100 ms:  Adequado para aplicações de tempo real suave
    Latência > 1 s:     Inadequado para aplicações de tempo real

  Relevância Acadêmica:
    Demonstra que protocolo híbrido em GMP é viável para IoT, mesmo sob
    emulação QEMU. Hardware real ARM seria significativamente mais rápido.

3.2 — CUSTO AMORTIZADO DE MENSAGENS

  Objetivo:
    Demonstrar que handshake assimétrico (X25519 + HKDF) é custoso uma
    única vez, mas mensagens subsequentes usam apenas cifra simétrica.

  Metodologia:
    Simula envio de 1, 10, 100 e 1000 mensagens (64 B cada) na mesma sessão:

    Cenário A: 1 mensagem
    ─────────────────────
      Custo total = handshake + 1×encrypt
                  = 3186 µs + 2 µs = 3188 µs
      Custo médio por mensagem = 3188 µs

    Cenário B: 10 mensagens
    ──────────────────────────
      Custo total = handshake + 10×encrypt
                  = 3186 µs + 20 µs = 3206 µs
      Custo médio por mensagem = 320.6 µs

    Cenário C: 100 mensagens
    ──────────────────────────
      Custo total = handshake + 100×encrypt
                  = 3186 µs + 200 µs = 3386 µs
      Custo médio por mensagem = 33.86 µs

    Cenário D: 1000 mensagens
    ──────────────────────────
      Custo total = handshake + 1000×encrypt
                  = 3186 µs + 2000 µs = 5186 µs
      Custo médio por mensagem = 5.186 µs

  Interpretação:
    • Handshake é 1500× mais custoso que uma mensagem
    • Em aplicações com múltiplas mensagens, amortiza rapidamente
    • IoT com envios ocasionais paga custo completo; contínuos ganham muito

  Tabela de Amortização:

    Mensagens   Handshake   Mensagens   Total      Custo/msg    Fator
    ──────────────────────────────────────────────────────────────────
    1           3186 µs     2 µs        3188 µs    3188 µs      1.0×
    10          3186 µs     20 µs       3206 µs    320.6 µs     10×
    100         3186 µs     200 µs      3386 µs    33.86 µs     94×
    1000        3186 µs     2000 µs     5186 µs    5.186 µs     615×

3.3 — THROUGHPUT DE CIFRA AEAD

  Objetivo:
    Medir vazão efetiva de ChaCha20-Poly1305 em diferentes tamanhos
    de payload e AAD, caracterizando performance de comunicação.

  Metodologia:
    Para cada tamanho de payload: {16, 64, 256, 1024, 4096, 16384 bytes}
    Para cada tamanho de AAD: {0, 16, 64, 128 bytes}

    1. Cifra 500 vezes, coletando tempo de cada operação
    2. Calcula throughput = payload_bytes / tempo_médio / 1e-6 (MB/s)
    3. Reporta por combinação (payload, AAD)

  Fórmula:
    Throughput (MB/s) = (payload_bytes × 500) / (tempo_total_µs × 1e-6)

  Saída Esperada:

    Payload (B)  AAD (B)  Tempo (µs)  Throughput (MB/s)
    ──────────────────────────────────────────────────
    16           0        2.3         6.9 MB/s
    64           0        2.0         32 MB/s
    256          0        5.3         48 MB/s
    1024         0        19.1        54 MB/s
    4096         0        73.5        56 MB/s
    16384        0        291.9       56 MB/s
    
    256          16       5.9         43 MB/s
    256          64       6.3         41 MB/s
    256          128      6.7         38 MB/s

  Interpretação:

    • Throughput satura em ~55-60 MB/s (limite QEMU)
    • AAD tem impacto menor (< 5% de degradação)
    • Pequenos payloads (16-64 B) têm overhead de setup
    
    Relevância:
      55 MB/s é adequado para IoT intermitente.
      Sensores que enviam ≤ 1 KB/s ocupam < 1% de CPU na cifra.

  Nota sobre QEMU:
    Throughput em hardware real ARM Cortex-A9 seria ~300-400 MB/s
    (puro ChaCha20 em assembly pode atingir 1+ GB/s).
    Números QEMU são conservadores e adequados para pesquisa.

4.3 — ESTATÍSTICAS ROBUSTAS

  Todas as métricas são calculadas da seguinte forma:

  Média:
    µ = (1/n) × Σ x_i

  Desvio Padrão (populacional):
    σ = √[ (1/n) × Σ(x_i - µ)² ]

  Mediana:
    x_med = x[n/2]  (após ordenação)

  Percentil 95:
    x_p95 = x[⌊0.95n⌋]  (discreto, sem interpolação)

  Percentil 99:
    x_p99 = x[min(n-1, ⌊0.99n⌋)]

  Justificativa de Escolhas:
    • Desvio padrão (não intervalo): quantifica variabilidade
    • Mediana + P95/P99: resumi casos outlier sem distorção
    • Percentis discretos: reproduzível em todas as plataformas

 LIMITAÇÕES E CONSIDERAÇÕES IMPORTANTES
═══════════════════════════════════════════════════════════════════════════════════

1. QEMU vs. Hardware Real
   ─────────────────────
   ⚠️  Tempos absolutos em µs obtidos em QEMU NÃO são válidos para hardware real.
       
       Validação:
         • Comparações relativas (A vs. B): válidas em QEMU
         • Escalabilidade (crescimento com n): válida em QEMU
         • Throughput absoluto (MB/s): invalido em QEMU
       
       Usar QEMU para:
         ✓ Demonstrar funcionamento
         ✓ Validar corretitude
         ✓ Comparar primitivas
       
       NÃO usar para:
         ✗ Estimar latência de produção
         ✗ Escolher entre implementações
         ✗ Comprovar requisitos de tempo real

2. GMP vs. Aritmética Especializada
   ────────────────────────────────
   GMP é flexível e portável, mas lento:
     • Sem constant-time
     • Alocação dinâmica
     • Sem limbs fixos
   
   Speedup esperado com aritmética de campo:
     3–10× mais rápido (limbs fixos + redução especializada)
   
   Uso apropriado de GMP:
     ✓ Prototipagem
     ✓ Pesquisa acadêmica
     ✓ Validação de corretude
   
   Não usar em produção sem otimização.

3. Falta de Testes RFC Oficiais
   ────────────────────────────
   ⚠️  Esta suite NÃO inclui vetores de teste oficiais das RFCs.
       
       Limitação aceita por:
       • Tamanho do código
       • Foco em benchmarking, não conformidade
       
       Para validação criptográfica completa:
         → Adicionar testes contra RFC 8032 vectors (Ed25519)
         → Adicionar testes contra RFC 7748 vectors (X25519)
         → Adicionar testes contra RFC 8439 vectors (ChaCha20-Poly1305)
         → Usar test framework (GoogleTest, Catch2)

4. Medição de Energia e Potência
   ──────────────────────────────
   ⚠️  Não implementado: energia, corrente, potência.
       
       Para medir energia:
         → Usar multímetro + shunt resistor
         → Usar power analyzer (ex: Joulescope)
         → Integrar corrente sobre tempo de execução
       
       Típico (estimado):
         • Ed25519 Sign: ~5 ms × 100 mW ≈ 0.5 mJ
         • Handshake: ~3 ms × 150 mW ≈ 0.45 mJ
         • Sensores IoT 1/hora: ~0.15 mJ + comunicação

5. Ausência de Medição de Cache
   ─────────────────────────────
   ⚠️  Não medido: cache misses, cache lines, memory bandwidth.
       
       QEMU não expõe eventos de hardware. Para análise real:
         → Usar `perf` (Linux): `perf stat -e cache-misses`
         → Usar Valgrind: `cachegrind`
         → Analisar em profundidade com hardware profiler

 INTERPRETAÇÃO ACADÉMICA DOS RESULTADOS
═══════════════════════════════════════════════════════════════════════════════════

Questão 1: "É viável implementar protocolo híbrido em IoT com GMP?"
Resposta:
  ✓ SIM. Latência total ~3 ms para handshake + 1 mensagem é aceitável
    para IoT não-crítica (sensores, gateways, smart home).
  
  ⚠️  NÃO para:
    • Aplicações de tempo real rígido (< 100 µs)
    • Dispositivos com processador < 100 MHz
    • Bare-metal sem SO

Questão 2: "Qual é o gargalo principal?"
Resposta:
  1º lugar: Multiplicação escalar de Curve25519 (~3100 µs por operação)
           → Causa: Aritmética modular GMP com campo de 255 bits
           → Solução: Limbs fixos + redução especializada (3–10× mais rápido)
  
  2º lugar: Verificação de Ed25519 (~10.5 ms duas mults. escalares)
           → Causa: Mesma que acima
           → Solução: Idem
  
  3º lugar: ChaCha20-Poly1305 NÃO é gargalo (~2 µs para 64 B)
           → Adequado mesmo em hardware lento

Questão 3: "Escalabilidade é O(n²) ou O(n³)?"
Resposta:
  Dados:
    160-bit: 1366 µs
    255-bit: 3120 µs (fator × 2.28)
    521-bit: 14858 µs (fator × 4.77 desde 255)
  
  Análise:
    Se O(n²):  521/255 = 2.04 → tempo ÷ 4.16 ✓ (próximo a 521²/255² ≈ 4.15)
    Se O(n³):  521/255 = 2.04 → tempo ÷ 8.5 ✗ (seria 14858/368 ≈ 40, não bate)
  
  Conclusão: Multiplicação é O(n²), redução também O(n²) → total O(n²)
             (Karatsuba em GMP, não algoritmo escolar O(n²) puro)

Questão 4: "Constante de tempo é garantida?"
Resposta:
  ✗ NÃO. GMP não oferece constant-time.
  
  Evidências de timing leak esperadas:
    • Variância de ~5–10% entre escalares de diferentes Hamming weights
    • Alocações dinâmicas causam jitter
    • Sem máscara bit-a-bit
  
  Para IoT?
    • Ameaça de timing é real mas menor que ameaça de força bruta
    • Atacante remoto via rede tem latência ≥ ms (mascara µs)
    • Usar para pesquisa; não para produção crítica

Questão 5: "Memória é suficiente para IoT?"
Resposta:
  Pico de heap: ~8 KB (521-bit)
  Stack típico: ~4 KB
  Total criptografia: ~12 KB
  
  Orçamento IoT típico:
    ESP32:        520 KB total → 95% disponível ✓
    Cortex-M4:    256 KB total → 96% disponível ✓
    Cortex-A9:    512 MB total → efetivamente ilimitado ✓
